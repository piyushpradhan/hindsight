WF 01

Record a run

Actor: agent developer · Precondition: SigNoz reachable via OTLP · Output: a replayable trace

Wrap the agent's LLM and tool calls. Every step becomes an OTel span (GenAI semconv); full payloads land as trace-correlated log records. Nothing else to change.

  1. Add the SDK and call startRun() at the top of the task.
  2. Wrap each LLM call in run.llm() and each tool call in run.tool().
  3. Close with run.end() tagging the outcome.
  4. Result: a full run reconstructable from SigNoz data alone.
const run = hindsight.startRun({ agentId: "researcher", taskId });

// LLM step — records request + response, emits gen_ai.* span
const resp = await run.llm(() => anthropic.messages.create(params), params);

// Tool step — records args + output, hashes args for mock-matching
const results = await run.tool("web_search", args, () => webSearch(args));

run.end({ outcome: "success" });   // or "failure" | "timeout"
Why it matters: span attributes have size limits, so spans carry metadata and hashes while correlated logs hold full messages. The engine joins them through SigNoz's ClickHouse schema.
WF 02

Replay a run

Actor: on-call engineer · Precondition: a trace_id · Output: a scrubbable timeline · Cost: $0.00

Pull a historical run from SigNoz and rebuild it as a RunGraph. You can inspect the recording step by step without calling a model or running a tool.

  1. Paste a trace_id (or open an incident from the inbox).
  2. Engine fetches spans by trace_id + correlated payload logs, normalizes to an ordered step list.
  3. Scrub the horizontal step timeline; each step expands to its transcript, tool I/O, and token/cost/latency badges.
  4. The failing step opens by default, with the request and recorded result in view.
# RunGraph step shape
{ index: 6, kind: "tool", tool: "web_search",
  request: {…}, response: "<malformed JSON>",
  tokens: { in: 1204, out: 88 }, cost: 0.003, latencyMs: 412,
  error: "tool_output_parse_error" }
Replay is read-only. It explains the recorded path; the fork workflow below tests a different one.
WF 03

Fork a run

Actor: engineer diagnosing a failure · Precondition: a replayed run · Output: a span-linked counterfactual trace

Pick a step and change one variable. The runner reconstructs state before that point, applies the mutation, and writes the branch as a new trace linked to the original.

  1. Select the step to fork from (e.g. step 6, the poisoned tool output).
  2. Apply one mutation (table below).
  3. Pick a mock policy for tool calls during re-execution.
  4. Run. Engine rebuilds conversation state up to step k, applies the mutation, re-runs live from there.

Mutation types (change exactly one)

MutationWhat it tests
swap modelWould Sonnet have recovered where Haiku spiraled?
edit system promptDoes one more constraint fix the behavior?
override tool outputIf the tool had returned valid JSON, does the run pass?
adjust paramsTemperature / max_tokens sensitivity.
disable a toolWas the wrong tool the trap?

Mock policy (how tools answer during re-execution)

ModeBehavior
strictAll tools answered from recordings (args-hash match). Unmatched call → fail fast. Pure test of the model's reasoning.
hybrid (default)Hash match → mock. No match → run live if the runner declares the tool safe; side-effectful tools (send, write, pay) return a dry-run stub.
liveEverything live; side-effectful tools still gated behind a confirm.
Safety: side-effecting tools never run live. Lineage uses an OTel span link, so SigNoz can show the fork beside its source through hindsight.fork.of.
WF 04

Incident loop

Actor: nobody (automated) · Trigger: a SigNoz alert rule · Output: an incident in the inbox, ready to replay

A SigNoz alert calls the engine with a trace-correlated event. The engine verifies the webhook, deduplicates it, and opens an incident.

  1. A provisioned alert rule trips (see triggers below).
  2. SigNoz fires a webhook to POST /hooks/signoz; labels carry agent.id.
  3. The engine resolves the trace and creates an Incident in SQLite.
  4. Studio shows the incident with its severity, agent ID, age, and source trace.
Alert ruleTrigger
Run failureserror rate > 20% over 5m, per agent (threshold)
Loop tripwireloop.score ≥ 3; this is the demo trigger
Latency driftSigNoz anomaly alert on p95 step duration
Cost spikecost-per-run anomaly, per agent
WF 05 · stretch

Diagnose with the SigNoz MCP server

Actor: engineer who wants a head start · Precondition: an open incident · Output: a proposed fork mutation

Diagnose would let an LLM query the run through SigNoz's MCP server and suggest a fork point plus mutation. This remains outside the current demo path.

  1. Open an incident and click Diagnose.
  2. The LLM pulls the run's spans/logs via the SigNoz MCP server.
  3. It returns a suggested fork point + mutation ("override step 6 tool output; it's malformed JSON").
  4. It pre-fills the fork panel; the engineer still starts the run.
Status: this workflow is a stretch item. Record, replay, fork, and compare work without it.
WF 06

Compare and verify

Actor: engineer · Precondition: original + fork traces · Output: a verdict, and a resolved incident

Two timelines, aligned. A diff computer matches steps (LCS on kind + tool name + args hash) and computes the deltas that matter.

Original · FAILED
14 steps · $0.41
malformed tool JSON → retry loop → garbage output
Fork · PASSED
4 steps · $0.09
tool output overridden → clean completion
  • Verdict card up top: outcome change, Δcost, Δtokens, Δsteps, plus a text diff of final outputs.
  • Links open both traces in SigNoz, where the span link exposes their lineage.
  • If the fork passes where the original failed, the engine marks the incident resolved-via-fork.
Verification rule: a successful fork isn't enough by itself. The engine also checks lineage, mutation evidence, and the absence of the original failure.
WF 07

Generate a postmortem

Actor: engineer closing the incident · Precondition: a resolved fork · Output: a markdown incident review

The engine fills a markdown template with incident data, measured deltas, and links to both traces.

## Incident 2026-07-22-researcher-loop

**What failed:** web_search returned malformed JSON at step 6 → retry loop
                (14 steps, $0.41). [trace 8f2a…](signoz://…)

**What changed:** override tool output with corrected JSON @ step 6

**Result:** 4 steps, $0.09, PASSED. [fork trace 3c1d…](signoz://…)

**Deltas:**  -10 steps · -$0.32 · outcome FAILED → PASSED
Implementation: this uses a fixed template. It doesn't call a model.
WF 08

Fleet monitoring

Actor: fleet operator · Precondition: agents recording · Output: dashboards and alert evaluations

Versioned dashboard JSON reports agent health and Hindsight's incident-to-resolution measurements.

Two dashboards (shipped as JSON in the repo)

  • Agent Reliability: success rate, incident count, p95 latency, and tool error rate per agent.
  • Hindsight Ops: incidents opened, forks run, time from creation to verified resolution, and the measured cost difference between a fork and full re-run.

Key metrics

MetricUse
runs.total{agent, outcome} → success-rate + error-rate alert
cost.usd.total{agent, model} → cost panels + anomaly alert
step.duration{kind} → p95 latency + anomaly alert
loop.scorerepeated (tool, args.hash) in last N steps; ≥3 = looping
incidents / forks / forks.resolvedcounts opened incidents, attempted forks, and verified resolutions
Service telemetry: the engine sends its own OTel data to the same SigNoz instance.
