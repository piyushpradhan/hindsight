Hindsight, on SigNoz

SigNoz stores the telemetry. Hindsight uses that data to replay and fork agent runs. This page maps the SigNoz features used by the project, then follows a run through the recorder, engine, and Studio.

01 · The platform

The parts of SigNoz that matter here

SigNoz is an open-source observability platform built on OpenTelemetry. It stores traces, logs, and metrics in ClickHouse and runs either on your own infrastructure or in SigNoz Cloud. Green tags mark the features Hindsight calls directly.

Signal · coreused

⌇Distributed tracing

Every operation is a span; spans form a trace (one end-to-end request). SigNoz renders them as waterfalls and flamegraphs, with service maps, span filtering, and span links that connect related traces.

Ingested over OTLP (OpenTelemetry protocol) on gRPC :4317 / HTTP :4318.

Signal · coreused

≡Logs management

Ingest, search, and filter structured logs. Pipelines can parse or enrich them. A log carrying trace_id and span_id points back to the span that produced it.

Signal · coreused

▲Metrics

Time-series counters, gauges, and histograms with labels. The query builder, PromQL, or ClickHouse queries can produce rates, p95/p99 percentiles, sums, and formulas.

Visualizeused

▦Dashboards

Dashboards combine panels from any signal. SigNoz imports and exports them as JSON, so this repository can ship the exact dashboard definitions it expects.

Reactused

⚡Alerts

Threshold and anomaly rules can watch metrics, logs, or traces. A fired rule sends a notification through a webhook, Slack, email, PagerDuty, or Opsgenie; Hindsight uses the webhook.

Correlationused

⋈One unified schema

Traces, logs, and metrics share a correlated schema in ClickHouse. Hindsight uses it to join a span with the log that holds its full payload.

Signal · derived

!Exceptions & errors

SigNoz groups captured exceptions, tracks their rates per service, and links each error to its source trace.

Signal · derived

⧗APM & service health

Built-in service views cover RED metrics (Rate, Errors, Duration), latency percentiles, Apdex, and dependency maps.

Queryused

⌗Query API

The REST query_range API (v3/v4) accepts builder queries. Hindsight's engine uses the same query shape as the SigNoz UI and authenticates with a role-scoped API key.

2026 · AIstretch

◇MCP server

SigNoz's Model Context Protocol server lets an LLM query observability data. A future Diagnose action could use it to suggest a fork mutation; the current replay path doesn't depend on it.

Deploy

⊞Self-host or cloud

Run the whole stack locally with Docker Compose (that's this setup: UI on :8080, ClickHouse + collector behind it) or use SigNoz Cloud. Same OTLP contract either way.

Foundation

◎OpenTelemetry-native

SigNoz accepts OTel and its semantic conventions, including the gen_ai.* fields that Hindsight writes for model calls.

02 · The mapping

How Hindsight uses each part of SigNoz

Hindsight reads its evidence from SigNoz. Traces hold run structure, logs hold full payloads, metrics feed dashboards, and alerts open incidents.

Pillar

⌇Traces

SigNoz stores each original run and each fork as its own trace.

Why it matters: a fully-recorded trace is a checkpoint you can re-execute. Span links tie each fork back to its original, so the lineage is visible inside SigNoz's own UI.

Pillar

≡Logs

Full LLM messages and tool inputs/outputs live as trace-correlated log records (marker hindsight.payload).

Why it matters: span attributes can't hold large message arrays. Payloads go to logs instead, and the engine joins them back by trace_id.

Pillar

▲Metrics

Metrics cover per-agent reliability, cost, tokens, latency, loop score, incidents, forks, and MTTR.

Why it matters: the same values feed dashboards and alert rules, including the measured cost difference between a fork and a full run.

Pillar

▦Dashboards

Two dashboards ship as JSON in infra/dashboards/: Agent Reliability and Hindsight Ops.

Why it matters: importing them shows success rate, p95 latency, opened incidents, attempted forks, and verified resolutions.

Pillar

⚡Alerts

Rules (error rate, loop score ≥ 3, latency/cost anomalies) fire a webhook into the engine at /hooks/signoz.

Why it matters: the authenticated webhook gives Hindsight a trace ID and opens an incident without polling.

Pillar · stretch

◇MCP server

An LLM queries SigNoz through the MCP server to propose the fork mutation.

Why it matters: it could shorten diagnosis, but the demo doesn't rely on it.

03 · The idea

What Hindsight adds

Hindsight records enough state to branch a failed agent run. Pick one step, change one input, and send the reconstructed state through the registered runner. Four components handle that path.

Component 1 · packages/recorder

●The Recorder SDK

A thin wrapper (not a framework). An agent developer changes ~4 lines: run.llm(...) around a model call, run.tool(...) around a tool call.

Each call becomes an OTel span. Spans carry metadata and hashes, while full payloads go to logs. The recorder emits tokens, cost, latency, and loop score as metrics.

Component 2 · apps/demo-agents

◑The demo agents

Two small agents cover research (web_search and calculator) and support triage (ticket_lookup). A CHAOS= flag injects malformed JSON, timeouts, or tool loops.

A seed script records roughly 30 mixed runs for the local dashboards.

Component 3 · apps/replay-engine

◭The replay engine

A Fastify service that reads SigNoz back: a query client, a RunGraph builder (spans + payload logs → an ordered step list), a fork executor, a diff/compare computer, the alert webhook, and a postmortem generator.

The service sends its own OTel data to the same SigNoz instance.

Component 4 · apps/studio

◧The Studio UI

A React debugger: an incident inbox, a run timeline you scrub step-by-step, a fork panel to change one variable, and a side-by-side compare with a verdict card.

A fleet strip up top links straight into the SigNoz dashboards.

The constraint: an ordinary trace doesn't store enough state to run again. Hindsight records messages and tool I/O as trace-correlated logs. When every required payload is present and its hash matches, the engine treats the run as a checkpoint.

05 · The loop

Three verbs: Record → Replay → Fork

Everything reduces to three actions and a loop between them.

Verb 1

Record

The SDK writes spans for structure, logs for full payloads, and metrics for cost, latency, and loops. A complete recording becomes a checkpoint.

Verb 2

Replay

The engine rebuilds a RunGraph from SigNoz. Studio shows every message, tool input, tool output, and token count without making a model call.

Verb 3

Fork

Pick a step, change exactly one thing (override a tool output, swap the model, edit the prompt, disable a tool). Re-execute from there; the runner replays unchanged tools from the recording. A new, span-linked trace proves the outcome.

The incident path: a SigNoz alert calls the webhook, the engine opens an incident for that trace, and an engineer tests one change. Hindsight resolves the incident only when the linked fork passes its verification checks. The postmortem links both traces.
06 · Honesty

Are the runs you see real?

The default demo reads real telemetry from SigNoz. The agent's model response may still come from the deterministic offline provider.

Reallive

✓The telemetry is real

The seed script runs the demo agents through the recorder. Their spans, payload logs, and metrics land in SigNoz, then the engine queries them back.

Simulated

◑The "brain" is deterministic

Without an API key, the agents use a deterministic offline provider at temperature 0. The provider scripts the answers; recording, storage, replay, and fork execution still use the running services.

Off by default

◧UI mock exists, but is opt-in

Studio also has fixtures for offline design work. They stay off unless the URL contains ?mock=1, which adds a fixture-data pill to the header. If the engine is down in normal mode, Studio shows the error.

Why simulate?

◎Deterministic on purpose

The offline provider makes the failure and fork result repeatable. Set the provider to Ollama or Anthropic to run the same path with a model.

In short: the offline provider scripts the agent responses. SigNoz storage, engine queries, checkpoint checks, fork execution, and comparison still happen in the running stack.
