Hindsight, on SigNoz

SigNoz is the observability platform. Hindsight is what we built on top of it. This page explains — in plain language, card by card — everything SigNoz can do, exactly which parts Hindsight uses, and how the whole system fits together.

01 · The platform

What SigNoz is & everything it can do

SigNoz is an open-source, OpenTelemetry-native observability platform — one tool for traces, logs, and metrics (an open alternative to Datadog / New Relic). It stores everything in ClickHouse, a columnar database built for fast queries over huge volumes. Runs self-hosted (Docker/Kubernetes) or as a cloud service. Below is the full menu of what it offers; the green tag marks the parts Hindsight leans on.

Signal · coreused

⌇Distributed tracing

Every operation is a span; spans form a trace (one end-to-end request). SigNoz renders them as waterfalls and flamegraphs, with service maps, span filtering, and span links that connect related traces.

Ingested over OTLP (OpenTelemetry protocol) on gRPC :4317 / HTTP :4318.

Signal · coreused

≡Logs management

Ingest, search, and filter structured logs. Log pipelines can parse and enrich. Crucially, logs are correlated to traces by trace_id/span_id, so a log record can be tied back to the exact span that produced it.

Signal · coreused

▲Metrics

Time-series counters, gauges, and histograms with labels. A query builder (plus PromQL / ClickHouse queries) turns them into panels — rates, percentiles (p95/p99), sums, and derived formulas.

Visualizeused

▦Dashboards

Compose panels over any signal into custom dashboards. They're config-as-code: exportable/importable as JSON, so a repo can ship dashboards that light up the moment someone imports them.

Reactused

⚡Alerts

Rules on metrics/logs/traces — both threshold and anomaly-based. When one fires it hits a notification channel: webhook, Slack, email, PagerDuty, Opsgenie. The webhook is the hook Hindsight rides.

Correlationused

⋈One unified schema

Traces, logs, and metrics share one correlated schema on ClickHouse. That single-store design is what lets Hindsight join a span back to its full-payload log in one query — the thing that makes replay possible.

Signal · derived

!Exceptions & errors

Captured exceptions are grouped and tracked, with error rates surfaced per service and linked to the originating trace for root-cause.

Signal · derived

⧗APM & service health

Out-of-the-box RED metrics (Rate, Errors, Duration) per service, latency percentiles, Apdex, and dependency maps — the standard application-performance view.

Queryused

⌗Query API

A REST query_range API (v3/v4) with a builder-query language. Programs — like Hindsight's engine — query traces, logs, and metrics the same way the UI does. Auth via a role-scoped API key.

2026 · AIstretch

◇MCP server

SigNoz's Model-Context-Protocol server lets an LLM query your observability data in natural language. Hindsight's optional "Diagnose" button would use it to propose a fix — garnish, not core.

Deploy

⊞Self-host or cloud

Run the whole stack locally with Docker Compose (that's this setup: UI on :8080, ClickHouse + collector behind it) or use SigNoz Cloud. Same OTLP contract either way.

Foundation

◎OpenTelemetry-native

No proprietary agent lock-in. SigNoz speaks OTel and its semantic conventions — including the gen_ai.* conventions for LLM calls that Hindsight follows for attribute hygiene.

02 · The mapping

How Hindsight uses each part of SigNoz

SigNoz isn't a viewer bolted on the side — it's Hindsight's system of record. Every pillar is load-bearing: the traces are the runs, the logs are the payloads, the alerts start the workflow.

Pillar

⌇Traces

Every original agent run — and every counterfactual fork — is stored as one trace.

Why it matters: a fully-recorded trace is a checkpoint you can re-execute. Span links tie each fork back to its original, so the lineage is visible inside SigNoz's own UI.

Pillar

≡Logs

Full LLM messages and tool inputs/outputs live as trace-correlated log records (marker hindsight.payload).

Why it matters: span attributes have size limits and can't hold whole message arrays — so payloads go to logs, and the engine joins them back by trace_id. This is the data that makes replay possible at all.

Pillar

▲Metrics

Per-agent reliability, cost, tokens, latency, and a loop score — plus meta-metrics: incidents opened, forks run, MTTR.

Why it matters: metrics feed the dashboards and the alert rules, and quantify Hindsight's own value (dollars saved by a fork vs a full re-run).

Pillar

▦Dashboards

Two dashboards ship as JSON in infra/dashboards/: Agent Reliability and Hindsight Ops.

Why it matters: import them and a living fleet appears immediately — success rates, p95 latency, and the meta-story of incidents → forks → fixes.

Pillar

⚡Alerts

Rules (error rate, loop score ≥ 3, latency/cost anomalies) fire a webhook into the engine at /hooks/signoz.

Why it matters: this is the front door. SigNoz doesn't just display the failure — it opens the case as an incident, no human needed.

Pillar · stretch

◇MCP server

An LLM queries SigNoz through the MCP server to propose the fork mutation.

Why it matters: a direct nod to SigNoz's newest feature — kept off the critical path so a demo never depends on it.

03 · The idea

The whole project, plainly

Hindsight is a flight recorder + time-travel debugger for AI agents. When an agent fails in production, today all you get is an autopsy — a waterfall of what already happened. Hindsight lets you act on the past: take a failed run, change exactly one thing, and re-execute from that moment to prove the fix. Four components make that work.

Component 1 · packages/recorder

●The Recorder SDK

A thin wrapper (not a framework). An agent developer changes ~4 lines: run.llm(...) around a model call, run.tool(...) around a tool call.

Each becomes an OTel span. The key trick: spans carry metadata + hashes; the full payloads go to logs. Tokens, cost, latency, and loop score are emitted as metrics.

Component 2 · apps/demo-agents

◑The demo agents

Two small agents — a research agent (web_search + calculator) and a support-triage agent (ticket_lookup) — plus a CHAOS= flag that injects realistic failures (malformed JSON, timeouts, tool loops).

A seed script runs ~30 mixed runs so the dashboards look alive instantly.

Component 3 · apps/replay-engine

◭The replay engine

A Fastify service that reads SigNoz back: a query client, a RunGraph builder (spans + payload logs → an ordered step list), a fork executor, a diff/compare computer, the alert webhook, and a postmortem generator.

It also instruments itself into the same SigNoz — dogfooding.

Component 4 · apps/studio

◧The Studio UI

A React debugger: an incident inbox, a run timeline you scrub step-by-step, a fork panel to change one variable, and a side-by-side compare with a verdict card.

A fleet strip up top links straight into the SigNoz dashboards.

The one clever bit worth understanding: a trace normally can't be re-run because it doesn't store enough. Hindsight fixes that by recording everything — every message, every tool input/output — as trace-correlated logs. Once the trace holds the full state, a fully-recorded run becomes a checkpoint, and a checkpoint can be re-executed. That's the whole thesis.

05 · The loop

Three verbs: Record → Replay → Fork

Everything reduces to three actions and a loop between them.

Verb 1

Record

The SDK wraps every LLM and tool step into SigNoz — spans for structure, logs for full payloads, metrics for cost/latency/loops. The trace becomes a checkpoint.

Verb 2

Replay

Pull any past run out of SigNoz, rebuild it as a RunGraph, and scrub it step-by-step in the UI — every message, every tool I/O, every token count. Zero LLM cost. VCR for agents.

Verb 3

Fork

Pick a step, change exactly one thing (override a tool output, swap the model, edit the prompt, disable a tool). Re-execute from there; unchanged tools are mocked from the recording. A new, span-linked trace proves the outcome.

The incident loop that glues it together: a SigNoz alert fires → webhook auto-creates an incident in the inbox → a human scrubs the timeline and spots the poisoned step → forks it with one fix → the compare view shows failed → passed, and the incident is marked resolved-via-fork. One click generates a postmortem with deep links to both traces.
06 · Honesty

Are the runs you see real?

Yes — the runs are real telemetry in SigNoz, not hard-coded UI data. But it's worth being precise about what "real" means here.

Reallive

✓The telemetry is real

Every run in the list is a genuine OTel trace in SigNoz's ClickHouse, produced by the seed script running the demo agents through the recorder. Real spans, real payload logs, real metrics — queried back by the engine.

Simulated

◑The "brain" is deterministic

There's no live Claude/GPT here (no API key), so the agents use a deterministic mock LLM at temperature 0. The intelligence is scripted — but the record → store → replay → fork pipeline is 100% real. Swap in a real model SDK and nothing else changes.

Off by default

◧UI mock exists, but is opt-in

The Studio has a fixture set for offline design work. It's OFF unless you open the app with ?mock=1, which shows a "mock data" pill in the header. No pill = real SigNoz data. There is no silent fallback — if the engine is down, the UI errors rather than faking data.

Why simulate?

◎Deterministic on purpose

A scripted agent means the demo can't faceplant live and a fork's result is reproducible — the same failure every time, the same fix every time. That's a feature for a debugger, not a shortcut.

One-line summary: the agents' thinking is faked so the demo is reliable; everything SigNoz stores and everything Hindsight does with it — recording, querying, replaying, forking, comparing — is genuinely happening against a live SigNoz instance.
